## 2026-08-06 Register TencentDB Agent Memory synthesis — Dr/Open-tier direction, nothing built

Read this session, full-text (not summarized from memory or from vendor marketing copy alone): TencentDB Agent Memory (`github.com/TencentCloud/TencentDB-Agent-Memory`, MIT, TypeScript, ~15.5k stars). User asked to study it and bring back whatever genuinely fits SkillMe's readout-genesis philosophy — not to import it wholesale, and not to treat SkillMe as memory-less while doing so. Files actually inspected across this session: root README + CHANGELOG.md, `MemoryCore/` (README, `src/core/record/l1-extractor.ts`, `l1-dedup.ts`, `src/core/persona/persona-trigger.ts`, `src/services/pipeline-worker.ts`, `src/services/timer-scanner.ts`, `SKILL.md`, `SKILL-MIGRATION.md`), `MemoryKnowledge/` (README, `openapi.yaml`), `MemoryProxy/` (README, `src/skill/core-client.ts`, `src/skill/skill-bridge.ts`, `src/skill/handler-glue.ts`). Every finding below went through an adversarial verify pass against SkillMe's own actual files (grep/read, not assumption) before being kept; several survivors were downgraded or reworded mid-review after that pass caught overclaims — same discipline as PR d413a01's own mid-review "formalizes A9" → "related but separate" correction.

**Comparison baseline — SkillMe is not memory-less.** SkillMe already runs a four-layer memory-like system in `communication_glossary/`: `kg_extract.py` (L1, deterministic no-LLM readout from one checkpoint) → expert-framework reasoning (L2, AI-interpretive, Open tier, no script — deliberately has no `kg_expert_layer.py`) → `build_glossary.py` (L3, mechanical merge) → `skill_plan.py` (L4, Dr-tier role/skill plan) → `kg_accumulate.py` (cross-checkpoint accumulation of the L1 word-graph, scoped per `principal_id`+`topic_tag`, idempotent on `checkpoint_certificate`, mirroring `doc_ecosystem_bridge/bridge.py`'s `already_ingested()` pattern). This is directly comparable prior art to TencentDB's L0→L3 chat-memory layering (raw conversation → atomic fact → scenario block → persona/core) and to its Skill-asset lifecycle (versioned artifact, private-by-default, explicit promote-to-shared step) — both systems independently arrived at "raw deterministic layer, kept separate from an interpretive/synthesized layer, kept separate again from a promoted/shared layer." Where they diverge, every time checked: TencentDB is a live, multi-tenant, network-served system (HTTP API, ACL resolved at call time, background job workers); SkillMe is a synchronous, single-operator, file-based CLI pipeline with no live service, no network surface, and no concurrent-writer problem. Most of what follows is excluded specifically because it solves a live-service problem SkillMe does not have today, not because the pattern is bad.

**Explicitly excluded / rejected, with reasons:**

- L1 memory extraction as a single fused LLM call (scene segmentation + semantic type/priority classification together) — conflicts with SkillMe's own L1 definition (deterministic, no-LLM, raw readout); the name "L1" would be actively misleading if reused for a step that also does interpretation.
- Hybrid FTS5+vector search fused by RRF — SkillMe has no query/retrieval surface at all today; nothing to attach it to (A5, don't build machinery for a problem not in front of us).
- Storage/runtime substrate (SQLite+FTS5, bound port, mandatory LLM-API dependency for extraction) — SkillMe's L1 is deliberately LLM-free; importing an LLM-dependent extraction requirement would collapse that separation, not just add unneeded infra.
- "Fully automated memory routing still under iteration" — vendor's own admitted limitation about their repo, informative about their maturity only, no structure to import.
- PersonaMem 48%→76% benchmark — **unverified external vendor-reported number, no independent reproduction found, no methodology or artifact located behind it. Never repeated as settled fact about anything, about TencentDB or about SkillMe. Two of TencentDB's own GitHub issues (#73, #106, both open 2.5+ months as of this session) dispute other benchmark figures in the same repo — reason for extra skepticism toward any of their self-reported numbers, not reason to trust this one more.**
- SWE-bench token-reduction claim disputed by a filed, unresolved recomputation issue — same unresolved-external-dispute treatment; not cited as fact in either direction.
- Currently-open correctness bugs in TencentDB's own pipeline (silent-no-op delete, ignored filter arg, wrong-field search bug) — informative about their maturity, not a mechanism; the general caution (always verify affected-row-count/filter application, never trust a bare boolean return) already follows from SkillMe's own A0/A6 and needs no import.
- Deploy-script cross-platform instability, repo maturity/issue-volume metadata, benchmark-reproducibility-as-recurring-thread — all admitted_limitation-shaped signals about the source repo's own maturity; logged as reasons for extra skepticism toward other TencentDB claims, not as SkillMe mechanisms.
- Version-pinning/optimistic-locking for concurrent skill edits — SkillMe already looked at this exact adjacent problem in `bridge.py` (atomic write-to-temp + `os.replace()`) and explicitly declined full locking as unnecessary complexity for a single-operator CLI tool, with a named revisit trigger that hasn't fired. Respecting that existing decision (A11) rather than reopening it because a new vendor example looked more sophisticated.
- Knowledge Service as a standalone HTTP microservice, dual-protocol memory-proxy gateway, "28 endpoints" framing, discovery-target-mismatch finding — all either vendor-prose-only, no checkable attachment point in SkillMe's current file-based architecture, or already-solved-differently.
- Wiki lifecycle idempotent-shell/decoupled-trigger claim — checked directly against `kg_accumulate.py`: SkillMe already has this (`ingested_checkpoints` skip-check), so it is not new direction, only the narrower ordinal-status-granularity idea survives (listed below).

**Surviving mechanisms — Dr-tier or Open-tier direction only, nothing built, no schema/kernel/protocol_version change:**

1. **Defensive LLM-call parsing discipline (Dr).** Pre-call quality/injection gate before spending any LLM call, bounded recent+background context windows, hard output-count cap, markdown-fence-strip → regex-extract → sanitize → single-repair-retry parsing. Reframed for SkillMe: the fail-closed path must emit an explicit status (`extraction_failed` vs `zero_found`) rather than an ambiguous empty list, so A6's zero/bottom separation isn't silently collapsed — applicable to any future SkillMe stage that calls an LLM programmatically (none exists today).
2. **L1 pipeline instrumentation (Dr).** Add per-run counts (input/extracted/decision-distribution) and phase latency to `kg_extract.py`/`kg_accumulate.py`, all as exact discrete integers/ratios — no continuum reframing needed, this candidate is already discrete-native. Telemetry-emission failures must log a distinct local failure marker rather than silently defaulting to "0," per A6.
3. **Migration-script pattern for a future protocol_version bump (Dr).** IF SkillMe ever ships a breaking format change to L1–L4 artifacts: a standalone migration script, mandatory `--dry-run` producing a finite inspectable diff before mutation, mandatory pre-run backup — loosely consistent with the spirit of A0/A11, not a formalization of either.
4. **Uniform response envelope, reframed (Dr).** Keep the transport-vs-business-result separation and a lineage-handle (`request_id`) field; do not reuse the vendor's binary success/fail code as-is — must add an explicit `scope` field (A0), a three-way `status` (checked_found / checked_absent / not_yet_checked) instead of a binary code (A6), and a `tier` field (Th_coqc/exact/finite_diagnostic/Dr/Open) per A12.
5. **Delete-never-blocks, abort-at-next-checkpoint semantics (Dr).** IF SkillMe's pipeline ever becomes a live/async job rather than a synchronous script: cancellation should signal a poll-point abort rather than error, and batch operations should return a finite itemized record (`succeeded[]`/`failed[{id,reason}]`), not a single boolean. Note: SkillMe's existing "checkpoint" (a static, hash-identified input artifact) is not prior art for this — the vendor's "checkpoint" is a live control-flow poll-point, a different concept sharing only the English word.
6. **Async job idempotent-create + finite terminal status enum (Dr).** If a long-running ingestion step is ever built in front of `kg_extract.py`: keep tuple-keyed idempotent creation (SkillMe's own `already_ingested()`/`checkpoint_certificate` pattern is independent confirming precedent, not something borrowed from this source) and a finite status enum (`pending`/`processing`/`ready`/`failed`) that keeps not-yet-processed structurally distinct from processed-success and processed-failure, per A6.
7. **Structural query surface over an accumulated graph (Dr).** If `kg_accumulate.py`'s cross-checkpoint word-graph ever gets a read API: exact-node lookup (never fuzzy without an explicit exact-vs-inferred tier tag, per A1), bounded-integer-depth relation traversal (never unbounded/continuum), and a mandatory separate indexing-status endpoint so "zero results" and "not yet accumulated" are never the same observable (A6). "Impact"/blast-radius-style output must be labeled a graph-distance readout, not a real-world-consequence claim (A4).
8. **Authorization-as-separate-control-plane pattern (Dr, for SkillMe or an adjacent ANSE.ASIA service such as ARAYA).** Keep "who may read record X" as a separate resolver call from "what does the query return," never folded into ranking/relevance. Structurally analogous to — not an instance of — A4 (authority vs evidence) and A8 (visibility policy must be declared as normative, never inferred from data). Fail-closed to empty on resolver failure is a deliberate security tradeoff that itself creates an A6 tension (a genuinely-empty authorized set and a failed check look identical to the caller) — any real adoption must preserve that distinction in an internal audit path even while staying empty-facing externally.
9. **Ownership-key vs audit-only writer-id separation (Dr).** Keep "who last wrote this record" (audit, informational) structurally separate from "who/what scope owns this record" (ACL, enforced) — analogous to A4's non-identity spirit, not an instance of it. Any unspecified-scope case must surface as an explicit unresolved marker, never silently default to a fixed value (A6).
10. **Discrete four-level visibility enum as a future normative field (Dr).** IF `kg_accumulate.py`'s `principal_id`+`topic_tag` partition key is ever paired with actual access enforcement (it isn't today — the current split is an unenforced storage-partition key, not an ACL check, and must not be described as one): a small discrete enum (private/team/restricted-with-explicit-ACL/agent-targeted) is structurally compatible with A5 and A8, and needs no float/continuum reframing since it's already ordinal.
11. **Skill data-model reference fields for a future versioned-artifact store (Dr).** `skill_id`, monotonic-integer `version`, `is_head` boolean pointer, `owner_*` fields explicitly declared as normative ACL data (A8, not empirical fact), integer timestamps. Explicitly excluded: the vendor's `SearchHit.score:number` extension — an unbounded continuum relevance float that would need ordinal reframing (same move already applied to ARAYA's 0.00–1.00 scale in PR d413a01) before any adoption near ranking/search.
12. **BM25-backed `cli.py search` with a three-way status split (Dr).** If SkillMe's existing `search "<th/en>"` command is ever backed by a real index: malformed-query and scope-not-found must stay distinct from zero-hits (A6); relevance is surfaced only as ordinal rank position, never the raw float score (discrete-first floor, same reframing as ARAYA's scale); a top hit must never be presented as correct/canonical, only as relevance-to-query-terms (A4).
13. **Skill artifact regeneration trigger, decoupled from "persona" framing (Open).** `build_glossary.py`/`skill_plan.py` currently have no documented regeneration trigger at all — not even a live automation problem yet, since nothing in this repo runs on a schedule. The content-emptiness check (a regenerated artifact that only echoes scaffolding must not count as "already built," mapping cold-start/empty/real-content onto bottom/zero/nonzero) and explicit-request-always-wins as a declared override are worth keeping on file as design inspiration, at Open tier only — no live attachment point exists to make this checkable yet.
14. **Various Open-tier footnotes**, each narrowed to a single reusable idea and explicitly excluded from anything built now: service_url self-description pattern (if SkillMe ever exposes a network-facing surface), write-protecting a synthesized artifact until independently cleared (if SkillMe ever gains mutable interpretive-layer storage — the independent-check half is SkillMe's own addition, not present in the vendor pattern), resolve-then-scope identity verification (if SkillMe/ARAYA ever crosses an untrusted network boundary), safer-default-plus-explicit-legacy-subpath versioning discipline (if a future protocol_version bump tightens a scoping invariant), self-verify-before-declaring-ready bootstrap discipline (no bootstrap script exists in SkillMe today to attach this to).

No code, schema, or protocol_version change. Pure documentation.
